### 2. `usePagedResult.cancelPending(id)` aborts in-flight controllers and starts a fresh request
File: `frontend/src/lib/usePagedResult.component.test.tsx`.

The hook does NOT expose `invalidate` on the returned controller — the public surface for aborting is `cancelPending(id?)`, which internally calls `invalidate` for the given id (or every tracked id when no id). That is the behavior to exercise.

Add a test (follow the file's existing `renderHook` / `deferred` / `makeState` patterns, do not invent new infrastructure):
- Mock `fetchPage` to capture each call's `AbortSignal` into an array and return a never-resolving promise (use `deferred<ResultPage>()`).
- Start one page fetch via `result.current.refresh(state.id)` (or `applyFilters`/`sortBy` — pick what the file already uses). Assert exactly 1 fetch recorded, signal not aborted.
- Call `act(() => { result.current.cancelPending(state.id) })`.
- Assert the first captured signal is now `aborted === true`.
- Start a second fetch via `result.current.refresh(state.id)`. Assert a second fetch is now in flight (`fetchPage` called twice, second signal not aborted). This proves the generation moved forward: if `cancelPending` had NOT bumped the generation, the second call's response would be treated as stale.
- Finally resolve the second deferred with a real page and assert `state.page?.rows` reflects it — proving the fresh request is "current" after the cancel.

(Rationale: `cancelPending(id)` → `invalidate(id)` → `abortFor(id)` (aborts registered controllers) + `generations.current.set(id, next)`. Both effects are observable through the above.)

### 4. `applyDataEpoch` ignores non-finite values
`applyDataEpoch` in `App.tsx` is a non-exported `useCallback`. Its body is literally:

    const n = Number(value);
    if (Number.isFinite(n)) setDataEpoch(n);

This invariant is not directly tested anywhere, and `App.component.test.tsx` only drives the happy path with real integer `data_epoch` values.

Options:

- Preferred (simplest): add a new test file `frontend/src/lib/applyDataEpoch.component.test.ts` that defines the exact same guard inline as a tiny pure function and tests the invariant. Document in a top-of-file comment that it mirrors `App.tsx`'s `applyDataEpoch` body verbatim, and that the mirror exists because the real callback is not exported (do NOT export it from `App.tsx` — tests only).
- Example skeleton:

      // Mirrors App.tsx:applyDataEpoch — kept in sync by hand.
      function applyEpochGuard(value: unknown, setter: (n: number) => void) {
        const n = Number(value);
        if (Number.isFinite(n)) setter(n);
      }

- Test that the setter is called for `0`, `1`, `42`, `"7"` (string parses to 7, finite — SHOULD call), and `3.14`.
- Test that the setter is NOT called for `null`, `undefined`, `NaN`, `"not-a-number"`, `"1.2.3"`, `{}`, `[]` only when non-finite (note `Number([])` is 0 — that WILL call; `Number({})` is NaN — won't).
- Use `vi.fn()` as the setter and assert `.toHaveBeenCalledWith(expectedN)` or `.not.toHaveBeenCalled()` per case.

Keep the file small (< 50 lines). Three or four assertions is enough — this is a guard test, not a numerical sweep.

The existing single test chains Select → Summarize `group_by` only. The gap: a renamed-away column simultaneously affects more than one downstream node type. This is the realistic Hermes scenario: one upstream rename, multiple downstream stale sites.

- Build Select fields using `reconcileSelectFields` where the user had `["region", "amount", "status"]` and upstream renames `region → region_2`. Confirm the Select retains the `region` tombstone with `isSelectFieldMissingUpstream` returning true.
- Model the Select's live output as the live upstream columns (post-rename): `const selectLive = ["region_2", "amount", "status"]`.
- Call `staleNodeflowColumnRefs("summarize", { group_by: ["region"], aggs: [{ col: "amount", func: "sum" }] }, { in: selectLive })`. Assert the result contains exactly `{ area: "group by", columns: ["region"] }`.
- Call `staleNodeflowColumnRefs("sort", { sorts: [{ col: "region", dir: "asc" }, { col: "amount", dir: "desc" }] }, { in: selectLive })`. Assert the result contains exactly `{ area: "sort", columns: ["region"] }`.
- Call `staleNodeflowColumnRefs("filter", { condition: "[region] = 'west'", field: "region", filterMode: "simple" }, { in: selectLive })`. Assert the result flags `region` under `area: "condition"` and `area: "field"`.

That proves one rename cascades to summarize + sort + filter in one assertion flow.
